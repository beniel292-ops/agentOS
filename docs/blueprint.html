AgentOS

An AI workforce for small service businesses. It starts with one job, done really well.

The one feature we build first: when a lead comes in, AgentOS reads it, scores it and drafts a reply. A person approves it with one click, then the email goes out. Every step is logged. That's the whole MVP. Everything else in this document comes later.

Who it's for

First customer: small digital marketing agencies (5–30 people) that lose leads because nobody replies fast enough or follows up. Later: consultants, education institutes and other service businesses.

Three things to decide once

  • A first test agency and 5–10 realistic sample leads. Fake but believable data makes the AI's work easy to judge.
  • The agency's facts sheet: services, price ranges and turnaround times. In v1 this is a plain settings field, not RAG.
  • Reply tone: friendly or formal, short or detailed. It goes into the prompt as a setting.
Rule for the whole project: build the smallest thing that is correct, then add to it. If the current phase doesn't need a tool, don't install it.

4 Architecture

Three pictures explain the whole MVP. Read them top to bottom.

A. The workflow: what happens to one lead

B. The system: which part talks to which

The web app never calls Claude or sends email itself. It only changes a lead's state; the worker does the slow and risky work.

C. Lead states: the state machine

TransitionWho triggers itWhat gets written
NEW → PROCESSINGThe worker picks up the jobAudit event, attempt count
PROCESSING → DRAFT_READYAI output passed validationExtracted details, score, draft
PROCESSING → FAILEDTimeout, API error or invalid output, after 3 triesError reason; a person can retry it
DRAFT_READY → APPROVED / REJECTEDA signed-in user of the same agencyWho, when, and the final text if edited
APPROVED → SENTThe worker sends exactly once (idempotency key)The provider's message ID

Five rules that keep it reliable

  • Tenant boundary: every table has a tenant_id and every query filters by it. This is covered by tests.
  • Idempotency: intake and sending both carry a unique key, so a double-submit or a retry never sends twice.
  • Allowed transitions only: one function owns every state change. Anything outside the allowed list is rejected.
  • Validate AI output: a Pydantic schema check runs first. Bad output is retried, then marked FAILED, and never reaches the user unchecked.
  • Append-only audit: audit events are inserted and never updated or deleted.

7 Step-by-step build prompts

Run these in Claude Code in order, one per branch. Don't move on until the Done when line is true, and commit after each prompt. Save this file as docs/blueprint in the repo so the prompts can point to it.

PROMPT 0Project rules
Create CLAUDE.md for AgentOS, a multi-tenant SaaS that helps small marketing agencies reply to leads.
MVP flow: lead intake -> AI extract/score/draft -> human approval -> email sent -> audit event.
Stack: Next.js + TypeScript + Tailwind + shadcn/ui (apps/web); FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic
(apps/api); PostgreSQL; Redis + arq; Claude API; Resend; Clerk.
Rules: every table has tenant_id and every query filters by it; no external message is sent before approval;
state changes only go through one transition function; audit_events are append-only; keep code minimal.
Done when: CLAUDE.md states the stack, the flow and the rules.
PROMPT 1Scaffold
Scaffold the monorepo described in CLAUDE.md: apps/web (Next.js App Router, TS, Tailwind, shadcn/ui), apps/api
(FastAPI managed by uv, Python 3.12), docker-compose.yml with Postgres 16 and Redis 7, .env.example, and a
Makefile with dev, test and migrate targets. Add GET /health to the API and a home page that calls it.
Add a GitHub Actions workflow that lints and tests both apps.
Done when: make dev starts everything and the home page shows "API: ok".
PROMPT 2Database + state machine
Add SQLAlchemy models and the first Alembic migration for tenants, users, leads, lead_analysis, drafts and
audit_events (columns as in docs/blueprint section 5). Lead status enum: NEW, PROCESSING, DRAFT_READY,
APPROVED, REJECTED, SENT, FAILED. Unique index on (tenant_id, idempotency_key); index on
(tenant_id, status, created_at). Write app/workflow/transitions.py with an ALLOWED map and
transition(lead, to_state, actor, data) that updates status and inserts an audit_event in the same
transaction. Add pytest tests for allowed and rejected transitions.
Done when: migrations run and the transition tests pass.
PROMPT 3Auth + tenants
Integrate Clerk in apps/web with organisations. In apps/api, verify the Clerk JWT, map the org id to a tenant
and user, and expose a get_current_tenant dependency used by every route. Add a test proving a user from
tenant A gets 404 for tenant B's lead.
Done when: the cross-tenant test passes and signed-out users are sent to login.
PROMPT 4Lead intake
Add POST /v1/leads, authenticated by a per-tenant intake API key, accepting name, email, company, message,
source and an Idempotency-Key header. A repeated key returns the existing lead instead of creating a new one.
Save as NEW, write an audit event and enqueue the arq job "process_lead". Add a simple test form page in
apps/web for submitting sample leads.
Done when: submitting the same lead twice creates one row and one job.
PROMPT 5AI step
Create app/ai/ with two functions using the Anthropic Python SDK and structured outputs:
extract_lead(lead) -> LeadAnalysis (intent, service, budget, urgency, fit_score 0-100, reasoning) and
draft_reply(lead, analysis, tenant_settings) -> Draft. Validate both with Pydantic. Keep prompts in
separate files. Use claude-haiku-5-5 for extraction and claude-sonnet-5-5 for drafting. Test with recorded
fake responses (no live API calls in CI).
Done when: the tests pass and a manual run on 5 sample leads gives sensible output.
PROMPT 6Worker + retries
Implement the arq job process_lead: NEW -> PROCESSING, call extract_lead and draft_reply, save the results,
then -> DRAFT_READY. Timeout 60s, max 3 attempts with backoff; after the last failure -> FAILED with the
error stored. The job must be safe to run twice (skip if already past PROCESSING).
Add POST /v1/leads/{id}/retry for FAILED leads.
Done when: killing the worker mid-job and restarting it finishes the lead with no duplicates.
PROMPT 7Approval inbox
Build apps/web pages: /inbox (lead list with status badge, fit score and time since arrival; filter by
status) and /leads/[id] (lead message, extracted details, editable draft, Approve and Reject buttons,
audit timeline). Add the API routes they need: GET /v1/leads, GET /v1/leads/{id},
POST /v1/drafts/{id}/approve (optional edited body), POST /v1/drafts/{id}/reject (reason).
Keep the layout clean and simple with shadcn/ui.
Done when: a user can approve or reject in the browser and the timeline updates.
PROMPT 8Send only after approval
On approval, enqueue send_reply. The job sends through Resend with an idempotency key built from the draft
id, stores the provider message id, and moves APPROVED -> SENT. It must refuse to send unless the lead is
APPROVED. Add a test that tries to send a DRAFT_READY lead and asserts nothing is sent.
Done when: approved replies reach a test inbox and unapproved ones never do.
PROMPT 9Acceptance tests + deploy
Write an end-to-end pytest covering the six acceptance criteria in docs/blueprint section 8. Add Sentry to
both apps. Deploy apps/web to Vercel and apps/api + worker + Postgres + Redis to Railway, running migrations
on deploy. Write a short README covering setup, environment variables and how to run the tests.
Done when: every acceptance test passes in CI and the production URL works end to end.

After the MVP: the first 30 days

  • Give it to 3 agencies for free and watch them use the inbox.
  • Track three numbers: time from lead to reply, the share of drafts approved without edits, and leads handled per week.
  • Choose Phase 2 or Phase 3 based on what they complain about most, not on what's most fun to build.
One sentence to remember: people trust AgentOS because a human approves every message and every action is logged. Protect that, and the features can grow safely.
